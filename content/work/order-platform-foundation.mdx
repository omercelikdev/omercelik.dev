## Context

A legacy ordering platform was being replaced by .NET microservices, one
service line at a time, with a team that would grow past ten engineers. Every
module the team would write needed the same answers: how a service is laid out,
how it logs, caches, calls other systems and runs background work, how requests
reach it, and how a developer runs the whole thing on a laptop. I set up that
foundation before the first feature was written.

## What I built

**One layout for every service.** Each module follows the same Clean
Architecture split into API, application, domain and infrastructure projects,
so a developer moving between modules already knows where everything lives.

**Shared building blocks.** Cross-cutting concerns live in one shared library
instead of being rewritten per module. I started it with logging, cache
invalidation, dependency registration and background jobs, and the team has
added to it since:

- Logs go to Kafka first and are written to the database in batches, so logging
  never slows a request down.
- When a service changes cached data, it publishes an invalidation event, and
  every pod clears its copy. Scaling out does not mean serving stale data.
- Calls to other services and downstream systems go through typed clients with
  retry and timeout policies.
- Services register themselves by attribute, so adding one is not a wiring
  exercise.

**A thin gateway.** New modules sit behind a YARP reverse proxy that routes by
module and finds services through service discovery. It deliberately does
nothing else: authentication stays where it already was during the transition,
so the new platform could grow without first rebuilding security.

**One command for the whole system.** A .NET Aspire app host brings up
everything a developer needs: Kafka, PostgreSQL, the legacy Oracle database,
the workflow engine, a mock server standing in for downstream systems, the UI
and every module, wired together through service discovery, with profiles per
product and environment.

## Outcome

A new module starts from a working skeleton instead of a blank project, and a
new developer runs the full system locally on day one. The team has since
extended the foundation well beyond what I first wrote, which is what it was
for.
