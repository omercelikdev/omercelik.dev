## Context

A legacy ordering platform was being replaced by .NET microservices, with a team
that would grow past ten engineers. Before the first feature, every module
needed the same answers: how a service is laid out, how it logs, caches, calls
other systems and runs background work, how requests reach it, and how a
developer runs everything on a laptop.

## The decisions

- **One layout for every service.** A developer moving between modules already
  knows where everything lives.
- **Logs go to Kafka first,** then to the database in batches, so logging never
  slows a request down.
- **Cache invalidation is an event.** A service that changes cached data
  publishes it, and every pod clears its copy. Scaling out never serves stale
  data.
- **The gateway stays thin.** It routes by module and does nothing else;
  authentication stays where it already was during the transition, so the new
  platform could grow without first rebuilding security.
- **One command for the whole system.** An Aspire app host brings up Kafka,
  PostgreSQL, the legacy Oracle database, the workflow engine, a mock server for
  the downstream systems, the UI and every module, with profiles per product and
  environment.

## Outcome

A new module starts from a working skeleton, and a new developer runs the full
system locally on day one. I set up the foundation; the team has extended it
since.
